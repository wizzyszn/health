## Part one — the MRN

Every patient now has a Medical Record Number, returned on their profile endpoints. Generated by the server; can never be set or edited by a client.

```
C-3622ET
└┬┘ └──6 uppercase letters/digits
 prefix    (always matches /^C-[A-Z0-9]{6}$/ — 8 chars total)
```

### Where it appears

| Endpoint                   | Returns `mrn`? | Notes                                                                                                                                          |
| -------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| GET `/patients/me`         | ✅ Yes         | Alongside `registration_no`                                                                                                                    |
| GET `/patients/me/profile` | ✅ Yes         | Full profile document                                                                                                                          |
| GET `/doctors/me`          | ❌ Never       | Doctors hold an MRN internally but it's stripped from every doctor-shaped response — including nested doctor objects in bookings/consultations |
| GET `/doctors/me/profile`  | ❌ Never       | 〃                                                                                                                                             |
| GET `/admin/doctors`       | ❌ Never       | Doctor lists carry `doctor_no`, not `mrn`                                                                                                      |

⚠️ **Don't build this:** no UI anywhere for showing or editing a doctor's MRN — the API will never return one; a field would render permanently blank.

### Strictly read-only

No update endpoint accepts `mrn`. Including it in a profile update body returns **400** `"property mrn should not exist"` — and the **whole request fails**, so all other fields in that payload are discarded too. Strip it before sending when round-tripping a fetched profile object.

```
PATCH /api/v1/patients/me
{ "first_name": "Ada", "mrn": "C-HACKED" }

→ 400  ["property mrn should not exist"]
   first_name is NOT saved — the request is rejected whole.
```

⚠️ **Two formats will exist in the wild:** older records still carry a legacy 9-char MRN with no prefix (e.g. `0LDWYI2UQ`). A migration converts these to `C-XXXXXX`; it has run on dev but **not yet on production**. Until then treat `mrn` as an opaque display string — don't validate against the regex or parse the prefix client-side.

ℹ️ Background only: MRNs come from one shared pool across patients and doctors (no collisions) — DB-enforced, nothing for clients to check.

## Part two — allergies & medical history

Three string-array fields on the patient profile, previously **unusable over file-upload requests**:

| Field                         | Type     | Meaning                                                        |
| ----------------------------- | -------- | -------------------------------------------------------------- |
| `allergies`                   | string[] | Known allergies                                                |
| `previous_medical_conditions` | string[] | Past conditions (**note the name** — not `medical_conditions`) |
| `medical_flags`               | string[] | Clinical flags surfaced to doctors                             |

### Endpoints accepting them

| Endpoint                      | Content type                | Who             |
| ----------------------------- | --------------------------- | --------------- |
| PATCH `/patients/me`          | multipart/form-data or JSON | Patient         |
| PATCH `/patients/me/profile`  | multipart/form-data or JSON | Patient (alias) |
| PATCH `/patients/:id/profile` | JSON only                   | Admin           |

(The patient routes accept multipart because they also take a profile image: `file`, `image`, or `profile_picture`.)

### What was broken

Multipart has no array type: a single `allergies` part arrived as a plain string and was rejected; two or more arrived as an array and passed. A patient could record **two** allergies but not **one**.

```
// BEFORE
-F 'allergies=Latex'                       → 400 "allergies must be an array"
-F 'allergies=Penicillin' -F 'allergies=Peanuts'   → 200 ✓

// AFTER — all four forms work
-F 'allergies=Latex'                       → ["Latex"]
-F 'allergies=Penicillin' -F 'allergies=Peanuts'   → ["Penicillin","Peanuts"]
-F 'allergies=["Sulfa","Iodine"]'          → ["Sulfa","Iodine"]
{ "allergies": ["Penicillin"] }            → ["Penicillin"]  (JSON body)
```

### Semantics — read before wiring the form

| You send         | Result                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------ |
| `["Penicillin"]` | **Replaces the entire list** — anything stored and not included is gone. Send the full set |
| `[]`             | Clears the list                                                                            |
| `""`             | Also clears (empty multipart value)                                                        |
| field omitted    | Left untouched — partial updates never wipe lists you didn't send                          |

🚫 **Commas are never split:** `"Peanuts, tree nuts"` stores as **one** entry — deliberate, so clinical entries can't silently fork. If your input is comma-separated text you **must split client-side** and send repeated parts or a JSON array; sending the raw string creates one malformed entry.

✅ **Suggested input pattern:** a tag/chip input beats free text — each chip becomes exactly one array element, sidestepping the comma problem. Pre-fill from `GET /patients/me/profile`; always submit the complete set since sends replace rather than merge.

### One more fix

`PATCH /patients/:id/profile` (admin) had **no documented request body** in Swagger — now fully documented.

## Errors you'll hit while integrating

| Request                       | Response                            | Fix                                                  |
| ----------------------------- | ----------------------------------- | ---------------------------------------------------- |
| Body contains `mrn`           | 400 `property mrn should not exist` | Strip before sending                                 |
| Any unrecognised field        | 400 `property … should not exist`   | Send only documented fields — extras aren't ignored  |
| `allergies` as number/object  | 400 `must be an array`              | Strings only                                         |
| `GET /patients/notifications` | 401 Access denied                   | Routes are `me`-scoped: `/patients/me/notifications` |

⚠️ **API-wide:** unknown fields _and_ unknown query params are rejected, never dropped. One stray key fails the whole request — round-tripping a fetched object into a PATCH will usually 400. Send only what changed.

## Verified behaviour (live instance)

- Patient signup returns a format-matching MRN on both profile endpoints.
- Admin-created doctors have DB MRNs that appear in **no** API response (create/list/profile).
- Forged `mrn` rejected with 400 on all four profile write paths.
- Single/repeated/JSON-array/JSON-body `allergies` all accepted; `[]` clears; omission preserves.
- `"Peanuts, tree nuts"` stored intact as one entry.

## Outstanding on backend

The legacy-MRN migration hasn't run on production yet — live records may still show the old 9-char format. Display as opaque string until it lands.
